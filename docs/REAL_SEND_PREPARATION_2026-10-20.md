## 앞선 제안 — 활성화 전 네 가지 조건

**이 절의 별도 서버 제한은 당시 제안이다. 단독 사용에 대한 사용자 확인 후 이번 시험에서는 개발을 생략하기로 했으며, 현재 실행 판단은 최상단 최신 결정을 따른다.** 전역 `ALLOW_REAL_ZENDESK_SEND`를 켜면 모든 operator/admin에게 실제 발송이 허용된다. 실제 모드 선택 자체가 첨부 업로드를 시작할 수 있으므로 보내기 버튼만 누르지 않는 것으로는 한정된 시험을 보장할 수 없다.

1. **서버 제한 구현·검증:** 승인한 실행자 UUID 1개, 정확한 수신처·내부 조직·그룹/담당자·폼/브랜드, PDF 1개의 크기·MIME·SHA와 연결된 업로드 토큰, 새 키 1개, 티켓 1건, autoSolve=false, 허용 기간을 고정한다. 수동/생성 문서 업로드·일괄 발송·직접 API 모두 같은 제한을 적용하고 임의 토큰·추가 요청은 외부 쓰기 전에 거절한다.
2. **알림·초기값 확인:** 조건부 webhook의 체크박스 초기값, 조직 자동 할당, 폼·상태, 추가 알림과 수신함 전달·자동 회신을 확인한다. 다른 고객 조직이나 추가 구독자가 발견되면 중단한다. 첨부는 합성 자료로 제한한다.
3. **시간·실행 승인:** 서버 제한과 모의 검증을 마친 뒤 시험 시간, 한 티켓·한 PDF, 허용할 추가 알림을 확정하고 실제 실행을 별도로 승인받는다. 현재 전역 플래그나 OAuth scope 변경을 요청하지 않는다.
4. **결과 불명·종료·정리:** 타임아웃·409·결과 불명이면 새 키로 다시 보내지 않고 같은 키와 티켓을 대조한다. 종료 시 발송 차단을 확인한다. 티켓 정리는 지연·해결 규칙을 검토한 별도 승인 범위다.

사용자가 다음 단계에서 정할 사항은 시험 시간·허용 기간, 수신함 외부 전달/자동 회신 여부, 한정된 실행과 추가 알림·정리 범위의 승인이다. 지금 신규 계정이나 비밀번호·비밀키를 추가로 받을 필요는 없다.

## 모의 검사와 실제 성공 기준

집중 검사 **기존 61개 + 신규 7개=68/68**, 대상 lint가 통과했다. 이번 src 변경 0이며 `tests/zendesk-oauth.test.mjs`의7개 시나리오·213행만 추가했고 배포 0이다. 68은 운영적용 당시 전체294와 다른집합이다. 신규7개는 PDF업로드 토큰→티켓 1건, 티켓POST401재전송금지, 자동 해결부분 실패/성공, 쓰기 scope거절, 업로드 토큰 누락/첨부 거절, 티켓첨부토큰거절을 검증한다. 외부 응답은 모의이며 실제 메일·첨부·티켓쓰기 성공을 증명하지 않는다.

이후 승인된 실제 시험에서는 업로드응답의 파일/토큰 → 실제 티켓ID/조직/그룹/담당자/폼/브랜드/첨부 → 지정수신함의 본문/한글/PDF열기 → 같은 키의 동일 티켓/이력 1건/추가 알림 여부를 대조한다. 업로드 자체와 댓글첨부는 다른단계다. [첨부 API](https://developer.zendesk.com/api-reference/ticketing/tickets/ticket-attachments/)

`attached_to_mail`은 dry-run첨부에서도 바뀔 수 있고 `auto_solved`만으로 실제 해결 성공을 판정할 수 없다. 결과응답·티켓·수신함으로 확인한다. 실제 쓰기권한·실수신은 미검증이며 아직 실행 승인이 없다.
