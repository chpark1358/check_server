# 역할별 권한과 검색 응답 검증 — 2026-10-16

## 범위와 현재 상태

- 대상은 `codex/preview-sandbox`의 고정 Preview다. 메인 브랜치·Vercel Production에는 배포하지 않는다.
- 사용자가 별도 테스트 계정이 없다고 확인했다. 실제 관리자·비로그인 HTTP 및 관리자 RLS 조회와 로컬 viewer/operator 테스트를 구분한다. 실제 일반 계정 간 격리는 아직 확인하지 못했다.
- DB는 Preview와 운영이 공유한다. 사용자 명시 승인 후 `202610160002_document_access_hardening.sql`을 적용하고, 추가 승인 후 `202610160003_profile_self_insert_hardening.sql`을 적용했다. 기존 사용자 역할·문서 데이터를 바꾸지 않고 접근 정책을 제한했다.

## 발견과 보완

1. 기존 `history/ticket-sends` API는 service-role 쿼리에 사용자 조건이 없었다. operator는 `sent_by=현재 사용자`, admin은 전체 조회로 보완했다.
2. 문서 메타데이터의 직접 UPDATE는 다른 파일 경로·만료일을 주입할 여지가 있었다. 다운로드·첨부·PDF 재시도 모두 `created_by/document_id/` 저장 경로 범위를 검사하며 traversal·인코딩 우회 경로는 저장소 접근 전에 거부한다. DB의 anon/authenticated INSERT·UPDATE·DELETE 권한은 회수했고 service_role 권한 3개는 유지됨을 확인했다.
3. 사용자별 고객사 매핑 저장은 DELETE 후 INSERT가 별도 요청이다. INSERT 실패 시 기존 본인 매핑이 없어질 수 있어 후속 원자적 저장 개선이 필요하다. 이번 권한 검증에서 변경하지 않았다.
4. 실제 DB의 `profiles_self_insert`는 본인 ID만 확인하고 역할 값은 제한하지 않았다. 현재 프로필 없는 인증 계정은 0개였지만, 향후 누락 계정이 생기면 높은 역할을 삽입할 여지가 있었다. 별도 승인 후 `id=auth.uid() AND role='viewer'`로 제한하고 정책을 다시 읽어 확인했다. 기존 프로필 UPDATE는 admin만 허용하는 상태다. 새 테스트 계정을 생성하거나 역할 상승을 실제 실행하지 않았다.

## 자동 검증

- 전체 182개 테스트 통과. 역할 테스트 11개는 실제 가드·route를 실행해 보호 API 31개 동작의 비로그인·하위 역할 차단, 3×3 역할 비교, user_metadata 승격 무효, 프로필 조회 실패 시 차단, 소유권·경로 검증을 확인한다.
- PDF 재시도·기존 경로 호환 및 잘못된 만료일도 회귀 검증한다.
- 검색 하니스는 10개 가상 시계 테스트로 요청 간격, 실제 동시성, 중단·시간 제한·예산, 결과 원문 제외를 검증한다.
- Preview 진단 페이지는 production 환경에서 404이며, 별도 토큰 추출 없이 현재 로그인 세션으로 기존 API를 호출한다. 계정 전환 시 이전 결과를 폐기한다.

## 검색 측정 계획

`/validation-preview`에서 관리자 권한 검사 11개가 모두 통과한 뒤 실행한다.

| 시나리오 | 쿼리 |
| --- | --- |
| 통합 이력 + 집계 | q=24123103, range=all, limit=50, includeSummary=true |
| 통합 이력 본문 | 위와 같음, includeSummary=false |
| 문서 검색 | q=24123103, range=all, limit=50 |
| 관리자 감사 검색 | section=audit, q=24123103, range=all, limit=25 |

- 첫 관측 각 1회 + 동시성 상한 1/2/4에서 시나리오별 각 6회 = 총 76회.
- 전역 시작 간격 최소 500ms, 초당 최대 2회, 실제 동시 요청 수도 기록한다. 상한 4가 실제 동시 요청 4를 보장하지 않는다.
- 상태 코드 오류, 10초 초과, 응답 원문 2MiB 초과, 비정상 응답은 중단한다. 관리자 `audit=search` 파라미터는 쓰지 않는다.
- p50/p95는 시나리오·단계별 nearest-rank 방식이다. n=6의 p95는 최대값이므로 소표본 참고치다.
- 첫 요청은 cold-start 증명이 아니다. 현재 소량 데이터·동일 계정·이 클라이언트에서의 관측이며 대규모 데이터나 다중 사용자 최대 처리량을 뜻하지 않는다.
- 검색 응답 원문·개인 식별정보·인증 토큰을 저장하지 않고 상태, 건수, 시간, 바이트, 요청 ID만 내보낸다.

## 실검증 결과

- 기능 검증 커밋: `a89437f`, Preview Ready. 메인 브랜치/Production 배포는 변경하지 않았다.
- 002 DB 변경 후 관리자·비로그인·서명 URL 발급·관리자 소유 문서 RLS 조회 11개 모두 통과했다. 비로그인 3개는 401, 관리자 조회 6개는 200, 파일 접근은 서명 URL 발급(리다이렉트를 따라가거나 URL을 내보내지 않음), RLS 조회는 예상 1행이었다.
- 실제 `pg_policies`에서 문서는 owner/admin SELECT만, 발송 이력은 operator 이상 본인 또는 admin SELECT만 남아 있는 것을 확인했다. 문서 버킷은 `public=false`, Storage 정책 2개 모두 직접 접근을 허용하지 않았다.
- 003은 측정 후 추가 승인·적용·정책 조건 확인을 했다. 프로필 INSERT를 별도 계정으로 실제 시도한 것은 아니다.

- 데이터 규모(측정 준비 시 DB 내부 집계): audit_logs 767, generated_documents 94, ticket_sends 41. 검색 일치: 이력 123건 중 50행, 문서 42건/42행, 관리자 감사 137건 중 25행.

첫 실행은 자동 승인 검토 서비스의 사용 한도 오류와 임시 브라우저 종료로 결과를 회수하지 못했다. 9/76회까지 관측한 불완전 실행은 최종 통계에서 제외했고, 위 수치는 새로 완료한 76회 실행만 사용했다. 결과 JSON·독립 재계산 JSON·HTML 보고서를 사용자 아티팩트 폴더에 보존했다.
