# 역할별 권한과 검색 응답 검증 — 2026-10-16

## 범위와 현재 상태

- 대상은 `codex/preview-sandbox`의 고정 Preview다. 메인 브랜치·Vercel Production에는 배포하지 않는다.
- 사용자가 별도 테스트 계정이 없다고 확인했다. 실제 관리자·비로그인 HTTP 및 관리자 RLS 조회와 로컬 viewer/operator 테스트를 구분한다. 실제 일반 계정 간 격리는 아직 확인하지 못했다.
- DB는 Preview와 운영이 공유한다. `202610160002_document_access_hardening.sql`은 적용 전 사용자 승인 대기다. 데이터 삭제 없이 문서 메타데이터의 클라이언트 쓰기를 제한하고 발송 이력의 소유자 범위를 좁힌다.

## 발견과 보완

1. 기존 `history/ticket-sends` API는 service-role 쿼리에 사용자 조건이 없었다. operator는 `sent_by=현재 사용자`, admin은 전체 조회로 보완했다.
2. 문서 메타데이터의 직접 UPDATE는 다른 파일 경로·만료일을 주입할 여지가 있었다. 다운로드·첨부·PDF 재시도 모두 `created_by/document_id/` 저장 경로 범위를 검사하며 traversal·인코딩 우회 경로는 저장소 접근 전에 거부한다. DB 직접 쓰기 제한은 별도 승인·적용 단계다.
3. 사용자별 고객사 매핑 저장은 DELETE 후 INSERT가 별도 요청이다. INSERT 실패 시 기존 본인 매핑이 없어질 수 있어 후속 원자적 저장 개선이 필요하다. 이번 권한 검증에서 변경하지 않았다.

## 역할 정책

| 기능 | 최소 역할 | 범위 |
| --- | --- | --- |
| 상태, Zendesk 조직·그룹·수신자 조회 | viewer | 공용 OAuth의 조회 범위 |
| 개인 설정·고객사 매핑 | viewer | 본인 |
| 직접 문서 다운로드 | viewer | 본인 또는 admin |
| CRM·문서 생성·재시도·첨부·발송 | operator | 문서 소유자 또는 admin |
| 일반 문서 목록·통합 이력 | operator | admin도 본인 범위 |
| 기존 발송 이력 | operator | 본인, admin은 전체 |
| 관리자 페이지·초대·공용 설정·서명 변경 | admin | 관리 범위 |

viewer도 공용 Zendesk 조직·수신자를 조회할 수 있는 것은 현 정책이다. 개인 Zendesk 계정의 권한을 물려받는 방식이 아니다. 조회 전용 역할의 업무 범위를 더 제한하려면 별도 정책 결정이 필요하다.

## 자동 검증

- 전체 182개 테스트 통과. 역할 테스트 11개는 실제 가드·route를 실행해 보호 API 31개 동작의 비로그인·하위 역할 차단, 3×3 역할 비교, user_metadata 승격 무효, 프로필 조회 실패 시 차단, 소유권·경로 검증을 확인한다.
- PDF 재시도·기존 경로 호환 및 잘못된 만료일도 회귀 검증한다.
- 검색 하니스는 10개 가상 시계 테스트로 요청 간격, 실제 동시성, 중단·시간 제한·예산, 결과 원문 제외를 검증한다.
- Preview 진단 페이지는 production 환경에서 404이며, 별도 토큰 추출 없이 현재 로그인 세션으로 기존 API를 호출한다. 계정 전환 시 이전 결과를 폐기한다.

## 검색 측정 계획

`/validation-preview`에서 관리자 권한 검사 11개가 모두 통과한 뒤 실행한다.

| 시나리오 | 쿼리 |
| --- | --- |
| 통합 이력 + 집계 | q=24123103, range=all, limit=50, includeSummary=true |
| 통합 이력 본문 | 위와 같음, includeSummary=false |
| 문서 검색 | q=24123103, range=all, limit=50 |
| 관리자 감사 검색 | section=audit, q=24123103, range=all, limit=25 |

- 첫 관측 각 1회 + 동시성 상한 1/2/4에서 시나리오별 각 6회 = 총 76회.
- 전역 시작 간격 최소 500ms, 초당 최대 2회, 실제 동시 요청 수도 기록한다. 상한 4가 실제 동시 요청 4를 보장하지 않는다.
- 상태 코드 오류, 10초 초과, 응답 원문 2MiB 초과, 비정상 응답은 중단한다. 관리자 `audit=search` 파라미터는 쓰지 않는다.
- p50/p95는 시나리오·단계별 nearest-rank 방식이다. n=6의 p95는 최대값이므로 소표본 참고치다.
- 첫 요청은 cold-start 증명이 아니다. 현재 소량 데이터·동일 계정·이 클라이언트에서의 관측이며 대규모 데이터나 다중 사용자 최대 처리량을 뜻하지 않는다.
- 검색 응답 원문·개인 식별정보·인증 토큰을 저장하지 않고 상태, 건수, 시간, 바이트, 요청 ID만 내보낸다.

## 실검증 결과

Preview 배포·DB 승인 결과·실제 HTTP 측정 후 기록한다. 현 문서는 코드 및 로컬 테스트 결과를 실제 계정 검증으로 대체하지 않는다.
