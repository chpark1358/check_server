## 병목과 변경

Supabase 프로젝트 설정에서 DB 지역 `ap-southeast-1`을 확인했다. 기존 검색 응답 헤더는 76회 모두 `iad1`이었다. 서버 처리 시간이 전체 요청의 평균 86.00–90.65%를 차지했고, 인증·프로필·DB 왕복이 주된 비용이었다. 브라우저의 본문 읽기 p50은 0.6–0.9ms, JSON 파싱은 0.1ms였다.

`vercel.json`에서 `/api/history/overview`, `/api/documents`, `/api/admin/overview`의 함수만 `sin1`로 지정했다. 배포 후 76개 응답이 실제 `sin1`임을 확인했다. 인증 서버의 사용자 확인, DB 역할 조회, 소유자 필터, 검색 쿼리, 응답 payload는 유지했다. 인증 캐시·공유 검색 캐시를 추가하지 않았다.

## 수치 해석과 남은 일

추가로 SQL Editor의 읽기 전용 트랜잭션에서 문서 목록·집계의 실제 검색 조건을 EXPLAIN ANALYZE로 확인했다. 현재 94행 중 42행이 일치했다. 목록(LIMIT 51)은 실행 0.520ms·계획 1.389ms, 집계는 실행 0.356ms·계획 0.248ms였다. 두 경우 공유 버퍼 디스크 읽기는 0이었다. 계정 해석용 InitPlan이 추가됐고 현재 시각·캐시의 단일 표본이므로 이전 API 측정의 완전한 재생이나 전체 검색의 대량 성능 검증은 아니다. HTTP·PostgREST·Auth 시간은 포함하지 않는다. 모든 진단 트랜잭션은 READ ONLY로 시작해 ROLLBACK으로 끝냈다.

`Server-Timing`은 Preview의 해당 GET 검색 경로에만 노출한다. `auth`, `profile`, `db`는 Supabase HTTP 왕복을 포함한다. `db_sum`은 겹치는 병렬 요청의 합이므로 `db`나 전체 시간에 더하지 않는다. 서버 시간은 앱 handler 기준이며 플랫폼 대기·콜드 스타트·본문 전송의 일부를 포함하지 않는다.

클라이언트 전체 시간과 서버 시간의 차이는 변경 후 p50 106–109ms다. 이 잔여 시간에는 전송·플랫폼·브라우저 스케줄링·본문 읽기·파싱이 섞여 있어 순수 네트워크 RTT로 표현하지 않는다.

실제 최대 동시 요청은 3 → 1이었다. 빠른 응답과 초당 2회 제한 때문에 변경 후 동시 4개 부하는 도달하지 않았다. 시작 간격 최소 622 → 519ms, 평균 시작률 0.623 → 1.014회/초다. 따라서 이 결과는 제한된 응답 시간 비교이며 수용량 또는 4명 동시 사용 보장이 아니다. 순차 A/B의 캐시·워밍·시간대·공유 서비스 부하 영향도 완전히 통제하지 못했다. 첫 관측은 콜드 스타트와 같지 않으며 반복 표본과 분리했다.

다음 성능 작업은 별도 비운영 데이터셋에서 1만·10만 건, 실제 겹치는 요청과 페이지 이동·복합 필터를 측정하는 것이다. 현재 작은 데이터셋만을 근거로 인덱스·검색 엔진·권한 캐시를 추가하지 않는다. 이번 지역 설정은 향후 main에 병합하면 Production의 같은 검색 함수에도 적용된다.

운영 전환 판단과 소스 백업·복구 조건은 [main 반영 검토](MAIN_ROLLOUT_REVIEW_2026-10-16.md)에 기록했다.
